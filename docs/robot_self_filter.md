# Robot self filter (module)

Removes the robot's own body from sensor data before it reaches mapping, collision
checking or perception. Without it the arm, base, lift and tool show up as obstacles, and
the planner refuses motions because the robot "collides with itself" as seen by the sensor.
It is a generic perception module: any robot, any sensor, any consumer.

Status: **core and a ROS node implemented** ([`src/perception/robot_self_filter`](../src/perception/robot_self_filter), 29 tests);
the node is a plain node (not a lifecycle node), nothing in the repo feeds it a live sensor yet, and the
sphere-model, GPU and learned implementations are not built. Design written from a review of an earlier production stack (a
point-cloud self filter run as a lifecycle node in front of mapping and in front of the
planning cloud) and from cuRobo v2's `RobotSegmenter` (see [curobo_v2_notes.md](curobo_v2_notes.md)).

## Role: mandatory stage right after raw data

Treat it as a generic stage of the perception chain, not an optional add-on. It runs
immediately after raw sensor ingestion and basic cleanup (range limits, NaN removal), and
before anything that fuses or interprets the data:

```
raw sensor ─► basic cleanup ─► RobotSelfFilter ─► fusion / mapping / segmentation ─► scene
(cloud, depth)  (range, NaN)    (this module)       (ESDF, voxel map, wall detection)
```

Everything downstream may then assume "the robot is not in the data".

## What already exists upstream (checked)

- **cuRobo v2 `RobotSegmenter`** (`curobo.perception`, source read at commit `78fd485`):
  segments the robot out of **depth images** by testing each depth point's distance to the
  robot's collision spheres (`distance_threshold`, default 5 cm), using forward kinematics
  from the joint state, with CUDA graphs. Returns a robot mask and a depth image with the
  robot removed. Input is a depth `CameraObservation`; the source has no lidar-cloud entry
  point. Its ESDF `Mapper` accepts lidar observations, but the segmenter itself is
  depth-image only.
- **Isaac ROS cuMotion `robot_segmenter`** ([docs](https://nvidia-isaac-ros.github.io/repositories_and_packages/isaac_ros_cumotion/isaac_ros_cumotion_robot_segmenter/index.html)):
  a ROS 2 node doing the same on depth streams from a URDF + XRDF and joint states; publishes
  the robot mask and the depth with the robot removed.
- **nvblox:** designed for depth cameras and / or 3D lidar, but no robot self-filtering was
  found in it. Its segmentation-mask input is for separating people, not the robot. So a
  self filter must run before nvblox, using one of the options here.

Consequence: for **depth cameras** we wrap cuRobo's `RobotSegmenter` (no reimplementation);
for **3D lidar and plain point clouds** nothing upstream covers it, so our own CPU
implementations below are the default. They use the same collision-sphere model, so
every path agrees on what "the robot" is.

## Where it sits

```
sensor (cloud / depth) ──► RobotSelfFilter ──► filtered cloud / depth ──► scene model,
                                ▲                                         ESDF / voxel map,
   joint state + TF + robot model                                          coverage perception,
   (+ attached tool / payload)                                             VAMP / cuRobo world
```

Every consumer of raw sensor data goes through it. Skipping it is the single most common
source of "ghost obstacle" planning failures near the arm.

## Port

```cpp
struct SelfFilterInput {            // core/, no ROS
  PointCloud cloud;                 // or DepthImage; with frame and per-point fields
  Time stamp;
  RobotState robot_state;           // joint positions at (or interpolated to) `stamp`
  Transform sensor_to_base;         // at `stamp`
};
struct SelfFilterResult {
  bool success; FailureCode code; std::string message;
  PointCloud filtered;              // robot points removed, other fields preserved
  std::vector<bool> removed_mask;   // aligned with the input points
  Stats stats;                      // removed count, latency
};
class RobotSelfFilter { virtual SelfFilterResult filter(const SelfFilterInput&) = 0; };
```

ROS shell (`ros/`): subscribes to the cloud, looks up TF, publishes the filtered cloud. The
design asks for a **lifecycle node** so startup can be ordered (the robot model and TF must exist
before configure); today it is a plain node that drops clouds until a robot description has arrived
(see "The ROS node" below).

## Implementations (swappable)

| Implementation | How it works | Pros / cons |
|---|---|---|
| `geometry_containment` | each link's collision geometry (box / sphere / cylinder / mesh hull, from the URDF) placed with FK, inflated by a per-link padding; points inside any inflated shape are removed | simple, exact to the model; CPU cost grows with links and points |
| `sphere_model` | the same collision-sphere model used by VAMP / cuRobo (generated by FOAM), so "what the planner thinks is the robot" equals "what is filtered" | one geometry source of truth; coarser than meshes |
| `depth_mask_gpu` | **wraps cuRobo v2 `RobotSegmenter`** (sphere-distance mask on depth images, GPU) | fastest for depth cameras; needs CUDA; depth images only |
| `learned_segmentation` | a segmentation network labels robot pixels | later; must stay behind the same port and be judged on the same benchmark |
| `null` | passes data through | tests, robots whose sensors never see the body |

## Behavior that matters (lessons from the earlier stack)

- **Containment vs. ray-casting.** Pure containment (is the point inside a link shape) only
  removes points on the robot. Adding a "shadow" test from the sensor origin removes
  everything occluded behind a link, which also clears real surfaces (it wrongly deleted
  ceiling points above the robot). Make the shadow test an explicit, off-by-default option.
- **Per-link padding.** One global padding is wrong: a thin forearm clip and a large
  wrist housing need different margins. Config: default padding per shape type plus
  per-link overrides. Start generous, tune down against recordings.
- **Minimum sensor distance.** Drop points closer than a threshold to a sensor mounted on
  the robot (its own mount and cable), cheaper than modelling them.
- **Preserve every point field** (color, semantic label, intensity, time). The filter must
  not strip a cloud to XYZ; downstream label-based steps (wall segmentation) depend on it.
- **Time alignment.** Use the joint state and TF at the cloud's own stamp, interpolated;
  using "latest" smears the arm into the scene during fast motion. Add padding proportional
  to link speed times the latency that cannot be removed.
- **Attached tool and payload.** The held tool (and anything it carries) is part of the
  robot model while attached and must be filtered; detach restores the environment.
- **Contact work needs care.** While the tool touches the wall, a padded tool shape removes
  the wall points right next to it. Provide a contact mode: reduced or zero padding on the
  contact link, and never remove points on the contact surface side of the tool tip.
- **Multiple sensors.** One filter instance per sensor (mobile base lidar, arm camera),
  each with its own sensor frame, padding and minimum distance, sharing one robot model.
- **Organized clouds.** Support keep-organized and replace-removed-with-NaN modes for
  consumers that need the image structure.

## Configuration (generic shape)

```yaml
self_filter:
  implementation: geometry_containment      # | sphere_model | depth_mask_gpu | null
  sensor_frame: ""                          # empty = containment only (no ray-casting)
  min_sensor_distance: 0.0
  keep_organized: false
  padding:
    default_sphere: 0.02
    default_box: [0.02, 0.02, 0.02]
    default_cylinder: [0.02, 0.02]
  links:                                    # which links count as "self"
    names: [shoulder_link, upper_arm_link, forearm_link, wrist_1_link, tool0]
    overrides:
      forearm_link: { box_padding: [0.04, 0.04, 0.04] }
  contact_mode: { link: tool0, padding: 0.0, active_when: tool_in_contact }
  time_alignment: { interpolate_to_stamp: true, speed_padding_gain: 0.0 }
```

## Evaluation

Record a bag of the arm moving through free space (nothing else in view) and one next to a
wall; label ground truth by geometry. Metrics, on the shared benchmark:

- **Leakage:** robot points surviving the filter (target: zero in free-space recordings).
- **Over-removal:** environment points removed (especially wall points next to the tool).
- **Latency and throughput** per cloud.
- Stability across robot configurations, including near-singular and fully extended poses.

## Relation to other modules

- Inputs the same **robot model** the planners use (URDF + collision spheres), so the
  geometry has one source of truth.
- Feeds the **scene model** ([architecture.md](architecture.md)), the cuRobo ESDF mapper and
  the VAMP point-cloud path (which clips to a region around the arm and downsamples after
  filtering).
- For depth cameras with cuRobo, the GPU mask path (`RobotSegmenter`) replaces the CPU cloud filter; lidar and cloud-only sensors use the CPU implementations.
- A GPU point-cloud variant (the same sphere-distance test applied to lidar points instead of depth pixels) is a plausible later implementation; not verified against the cuRobo code.

## What is implemented

| Piece | Detail |
|---|---|
| `UrdfRobot` | URDF text parsed with tinyxml2 (no ROS, no urdfdom version drift): link collision shapes (box, sphere, cylinder; meshes become their bounding box through a caller-supplied resolver, otherwise they are skipped and listed), joint tree, forward kinematics for fixed / revolute / continuous / prismatic joints and mimic joints |
| `SelfFilter` | containment test against each link's padded shapes; per-shape-kind padding with per-link overrides; `links` selects what counts as self; `min_sensor_distance`; optional `shadow` (points hidden behind a link, off by default); `speed_padding_gain` (more padding for fast links); contact mode (reduced padding on the contact link only) |
| Output | kept points with labels and colors still aligned, a per-point removed mask, and counts per link |
| Checks | on the rendered generic mobile manipulator: 99.5%+ of points sampled on the robot's surface are removed and none of 5,000 free-space points are; the filtered region follows the lift; 200k points x 15 shapes in well under a second |

The caller supplies link poses at the cloud's time stamp, so this core stays free of ROS; the ROS
node (next section) does that lookup. For depth cameras with cuRobo the GPU `RobotSegmenter` path
replaces this one, behind the same port.

## The ROS node

`self_filter_node` (`src/ros/self_filter_node.cpp`, node name `self_filter`, launch
`self_filter.launch.py cloud_in:=... cloud_out:=...`, example parameters in `config/self_filter.yaml`):

- subscribes `cloud_in` (`PointCloud2`, sensor QoS) and `contact_mode` (`std_msgs/Bool`, transient local);
  publishes `cloud_out` (the cloud with the robot's points removed, other fields kept);
- takes the robot from the `robot_description` parameter, otherwise from the `robot_description` topic;
  mesh collision shapes become their bounding box if the mesh (`.stl` / `.obj`, via `package://` or
  `file://`) can be read, otherwise they are skipped with a warning;
- looks up TF from the cloud frame and from each link to `root_link` at the cloud's own time stamp
  (the TF buffer interpolates); there is no joint-state subscription, the link poses come from TF alone;
- drops a cloud, with a throttled warning, when TF is missing or the filter fails, instead of passing
  it through unfiltered;
- parameters: padding per shape kind with per-link overrides, `links`, `min_sensor_distance`, `shadow`,
  `contact_link` / `contact_padding`, `tf_timeout_sec`.

Not built: a lifecycle node, a live sensor wired in (no simulated or real depth / lidar source exists in
the repo, see [ROADMAP.md](ROADMAP.md) section 1), the `sphere_model`, GPU depth-mask and learned
implementations, organized-cloud modes, and the optional mask output.
