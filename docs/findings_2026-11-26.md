# Findings from the November 2026 working session

Written 2026-11-26 so the evidence survives the chat it came from. Every number below was read from a log,
a test result or an API response during the session; where something is a guess, a single run, or was
never run, it says so. Nothing here ran on hardware.

## How to read the claims

- **Verified** means I (not only the helper that wrote it) ran it: an export of the branch built and tested in
  the Jazzy image, or the simulator run repeated.
- **One run per row** unless stated. Passes vary with machine load; the same seed gave different outcomes in
  the odometry-noise runs because the drive timing differs.
- **Machine:** one workstation, RTX 5080 (16 GB), 32 cores, 62 GB RAM, Docker with the NVIDIA runtime. Not
  the 4 GB laptop the planner timing question was about.
- Images used: `motion-planner:sim-gazebo` (Jazzy, Gazebo Harmonic, MoveIt, no GPU) and `motion-planner:gpu`
  (torch 2.8 with CUDA 12.8, cuRobo v0.9.0), built from `docker/Dockerfile`.

## Gravity compensation (#220)

- `gravity_core` equals MuJoCo's own gravity term to 5e-10 N m over 1000 random poses on the UR10e plus
  telescopic lift, with and without a 0.8 kg tool payload.
- With MuJoCo's free `gravcomp` removed and the repo's actuator law, a plain PD sags the tool 33 to 73 mm;
  the feed-forward brings that under 0.02 mm.
- Single-stand manager pass, one run per mode: `mujoco` and `core` both pass (coverage 100 %, peak 20.5 and
  19.5 N, tilt 0.18 and 0.20 degrees, wall gap 0.81 and 0.73 mm); `none` fails at the first planning segment
  (cause not traced).
- Gazebo: the arm holds its pose without any feed-forward, and the joint effort Gazebo reports at rest equals
  `gravity_core` to three decimals at five poses. The lift differs by 29.4 N until the two mimic stages are
  counted separately (0.5 x 39.2 + 0.5 x 19.6), which is a definition difference, not an error.
- **Two-stand pass with `gravity_comp:=core` passes on a clean build:** coverage 100 %, 2772 strokes, peak 24.1 N,
  tilt 0.135 degrees, gap 1.0 mm, 571 s (baseline 2767 strokes, 22.6 N). The first attempt (tilt 173 degrees) was
  invalid: a shared install tree had been rebuilt from another branch, so the xacro lost the new parameter and
  the feed-forward was never switched on. One run.
- Wart to fix: the xacro emits empty `gravity_payload_*` parameters when no payload is set, which makes the
  controller manager print "text not specified" warnings on every MuJoCo launch.

## Planner timing: why cuRobo "takes 12 to 16 s" (#225, #228, #231)

Seventy-six plans per row (19 logged docked poses to stow and back, two repeats), empty world, 7-joint config
(694 spheres), RTX 5080.

| condition | solved | median | p95 | worst | failed plans, median |
|---|---|---|---|---|---|
| idle | 72/76 | 25 ms | 1.32 s | 5.9 s | 5.5 s |
| about 3 GB VRAM free | 72/76 | 26 ms | 1.33 s | 7.3 s | 5.3 s |
| GPU and CPU shared (stand-in for the simulator) | 72/76 | 87 ms | 6.32 s | 26.7 s | 16.8 s |
| idle, `max_attempts` 6 | 72/76 | 25 ms | 0.45 s | 5.3 s | 2.4 s |
| shared, `max_attempts` 6 | 72/76 | 66 ms | 1.21 s | 13.9 s | 6.0 s |

- A normal plan is fast (all 64 on the normal route took 30 ms or less idle). The 12 to 16 s is the
  **fail-and-retry path under contention**: a failing plan takes about 17 s shared against 5.5 s idle.
- VRAM is not the limit: the planner used 1.2 GB.
- `max_attempts` 6 solved the same 72 problems and cut the shared failed-plan time from 16.8 to 6.0 s. The
  graph-seed fallback is not bounded by it (worst 13.9 s shared).
- Telemetry (#228): a failing plan reads 0.12 s inside cuRobo and 2.9 s wall, so the planner's own planning
  time hides most of a failed plan. Wall time is the number to watch.
- **Root cause of the unsolvable pair (`docked_wall_column_10`, both directions):** a joint winding mismatch.
  Its `shoulder_lift` is +2.72 rad, stow is -1.57; both endpoints are valid, the straight line is invalid, and
  the graph planner fails to connect the two windings (trajectory optimisation is never reached). Wrapping
  only `shoulder_lift` by a whole turn solves all 76 plans without disturbing the others; wrapping every joint
  toward stow also solves all 76 but moves the slow fallback to columns 8 and 9; wrapping each goal toward its
  start fixes stow-to-docked and worsens docked-to-stow (70 of 76).
- In the passes the dock poses sit at `shoulder_lift` 2.4 to 2.7 because `dock_seed_joint_state` is +2.79, so
  this mismatch occurs naturally. The existing README blames "low lift with the arm swung out"; the winding is
  the better-supported cause. **Not tested end to end with cuRobo in a pass.** The real start state cannot be
  re-expressed, so the lever is which winding the dock IK solution lands on (the seed, or the dock choice).
- Not measured: a wall in the world, the laptop's own GPU and CPU, the real simulator instead of the stand-in,
  more than one run per row, why the fallback plans on columns 9 and 18 are slow.

## Lift weighting and `joint_costs` (#222, #224, #235)

- The 2.0 lift cost lived in three opt-in places (OMPL candidate scoring, cuRobo quality mode, the manager's
  dock IK choice) and none of them is a cost inside a planner: they rank finished candidates. VAMP and the
  Cartesian planner have none. Two unit conventions existed: range-normalised in OMPL and cuRobo, raw metres
  in dock IK.
- #224 makes one array in the profile (`joint_costs`, size N, lift first, absent = lift 2.0 and arm 1.0), one
  rule (a joint's travel as a fraction of its range times its entry), read by dock IK, the OMPL plugin and the
  cuRobo node. **Behaviour change in an opt-in path:** with the array present the dock IK ranking is
  range-normalised instead of raw metres times 2.
- A real two-stand MuJoCo pass with `dock_ik_continuity` on and the array present passes (coverage 100 %, 2785
  strokes against 2767, peak 21.3 N, tilt 0.142 degrees, gap 0.9 mm), comparable to the baseline.
- The same pass with the reach preference (`reach_fraction` 0.8) failed once (coverage 0): the dock choice was
  "over the target" (0.86 against 0.80) and the OMPL approach was aborted. A controlled A/B on clean per-branch
  builds, same options, array present versus removed, **passes both ways**: with `joint_costs` coverage 100 %,
  2797 strokes, peak 19.3 N, tilt 0.134 degrees, gap 0.7 mm; without it 2814 strokes, 18.4 N, 0.140 degrees,
  0.8 mm. So the failure was not caused by #224; the earlier run most likely used a stale or shared build
  (not proven). One run each.
- The mixed-unit jump audit (#222) found no unweighted lift-versus-arm comparison at default settings; raw
  lift metres are compared with a radian limit by design in `max_dq_rad` and the exclusion tolerance.

## How far the simulators are from a real robot

Present: one depth camera (MuJoCo: a ray cast on scene geoms only, no robot self-hits, no texture; Gazebo:
rendered, sees the robot's own links; 96 x 64, 60 degrees, 0.1 to 5 m, 5 Hz), a fixed RGB camera in Gazebo
only, a wrist F/T sensor, joint encoders, and `/odom` equal to the simulated base pose. Noise is off by
default; MuJoCo has opt-in F/T and joint noise and control delay.

Absent at the start of the session: lidar or any laser scan, IMU, wheel encoders, localisation, bumpers and
cliff sensors, realistic camera behaviour, dynamic obstacles, e-stop inputs, any real sensor driver. The
simulated stand-arrival errors therefore measure the controller on perfect odometry, not navigation.

### Lidar (#239), verified on a merged build
- Both simulators now publish `LaserScan` on `/scan` (`lidar:=true`); the MuJoCo plugin never scans the robot's
  own bodies; Gazebo's `gpu_lidar` renders headless in the image (9.9 Hz, 541 rays).
- Obstacle stop, MuJoCo: without the lidar the base drives into the box (footprint gap -0.003 m, navigation
  stuck after 20 s); with it the result is `OBSTACLE` at a 0.301 m gap against a 0.30 m stop distance, and the
  scan range matched the true geometry (1.000 m). Gazebo (helper's run): 0.299 m.
- A real navigator bug was fixed on the way: while held, the navigator forgot its direction of travel, so the
  hold timer reset every cycle and the base crept into the obstacle. No unit test covers the fix, only the run.
- A front-mounted lidar loses an obstacle once the base turns or strafes past it; the scenario approaches
  straight ahead.

### Odometry and depth noise (#240)
- With `typical` odometry noise the navigator always meets its tolerance on the odometry it reads
  (6.5 to 11.3 mm, 0.008 to 0.015 rad), but against the truth the heading misses 0.03 rad in 4 of 6 seeds
  (0.048, 0.237 with a slip event, 0.053, 0.088; seeds 4 and 5 pass). My repeat of seeds 2 and 4 passed both:
  outcomes vary between runs even for a fixed seed.
- Wall docking is robust (4.8 mm against `/odom`, 5.0 mm against the truth) because it regulates on the
  detected wall plane.
- Depth noise: wall plane fit rms 0.00 to 2.62 mm (MuJoCo) and 0.00 to 2.36 mm (Gazebo), both pass.
- Self filter on the Gazebo cloud: 45 of 376 points removed (wrist and forearm), 0 of 331 wall points, wall fit
  unchanged. The wiring in the multi-stand scripts was never run in a full pass; the shipped self-filter
  config crashed the node (fixed); `tool_tip_link` is not in TF in Gazebo, so the tool itself stays unfiltered.

## Real platforms, SDKs and drive modes (#235, #236, #237)

- The repo already had real bases as generic xacro (AgileX Ranger Mini 2.0, Scout, Scout Mini, Husky, Jackal,
  Dingo-O, MiR100, MPO-500, TurtleBot3, TIAGo- and Fetch-style). What was missing was their sensor suites
  and a statement of which numbers are verified. The base catalogue document added in #235 has about 60 sourced numbers and
  about 50 marked unverified.
- Datasheet versus profile differences (profiles not changed): Ranger Mini mass 70 versus 64.5 kg and clearance
  0.04 versus 0.107 m; Scout Mini speed 1.7 versus 3 m/s and width 0.524 versus 0.58 m; Husky track 0.5708 versus
  0.55 m; Dingo-O body 0.506 x 0.464 versus 0.686 x 0.517 m and speed 1.1 versus 1.3 m/s; MiR100 wheel radius 0.1
  versus 0.0625 m; MPO-500 speed 1.0 versus 0.8 m/s; TurtleBot3 Burger length 0.16 versus 0.138 m.
- **SDK decision (#236): no submodules for vendor code.** Apt where the distro ships the package, otherwise a
  vcstool file with exact pinned commits (`docker/platforms.repos`, 12 pins re-verified), always through a thin
  adapter over ROS interfaces. Licence red flags: AgileX LICENSE files say Apache-2.0 while package.xml says
  BSD; the Neobotix robot packages have no LICENSE file and two of their packages are GPL-3.0 and AGPL-3.0
  (never link or vendor); MiR, TIAGo and Fetch have nothing usable on Jazzy. The Ranger Mini selects its mode
  from the incoming Twist and a CAN command, not through a ROS service.
- **Drive modes (#237):** `base.modes` with Ackermann, crab, spin, diff and skid; a mode-aware planner (Hybrid A*
  with Reeds-Shepp for Ackermann) and follower, opt-in. Ranger Mini 2.0 manual figures used: Ackermann minimum
  radius 0.81 m, top speed 1.5 m/s but 0.75 m/s once steering exceeds 20 degrees, spin up to 3.259 rad/s. The
  simulators do not enforce modes yet, and wall docking still assumes the base can move sideways.

## Isaac Sim as an optional add-on (#238)

- Runs as a sibling container next to the ROS image (NVIDIA's image cannot be layered into ours), joined by
  Isaac's ROS 2 bridge; nothing in the default stack depends on it.
- Smoke test from cold caches against a real container: pass in 128 s (all 7 checks: clock and joint states,
  joint order, holds under gravity, mimic stages follow the lift, a command reaches its target and holds).
  Helper's numbers: app start 11.5 s cold, 3.2 GB VRAM with the bridge graph, 120 Hz.
- Found the hard way: the Isaac image's entrypoint ignores a script given to `docker run`; Fast DDS picks shared
  memory between the two containers and no data arrives (a UDP-only profile fixes it); the URDF importer's mimic
  output for the lift is wrong (limits and a soft constraint that sags 4 cm) and has to be corrected.
- Not done: ros2_control interface (`hardware:=isaac`), wall world, F/T sensor, cameras, base motion, manager
  pass, CI. Natural next use: physically based lidar, depth and IMU.

## CI failures and the fix (#227)

- Of 21 PRs, four builds failed and every failure was an apt error from Canonical's hosts in the image build
  step, before any repository code was built: an index size mismatch ("Mirror sync in progress?"), a 404 on
  `libtiff6` after a 33 minute install, and a 404 on `libasound2`. They cleared on their own later.
- `archive.ubuntu.com` and `security.ubuntu.com` are the same servers (the same 91.189.91.8x addresses in the
  errors); the size-mismatch error reproduced through `archive.ubuntu.com` from the workstation, so changing the
  hostname does not help.
- #227 adds retries (three tries, a fresh index each time, also around `rosdep install`) and an opt-in
  `UBUNTU_MIRROR` build argument that CI sets to the Azure mirror. From the workstation the Azure mirror gave
  three clean index updates in a row and the failing packages downloaded. The argument was built into the base
  stage by hand (both apt sources switch with it, unchanged without it).

  (conda based) cannot build, which blocks generating VAMP robot headers and the VAMP side of the planner

- Disk was at 97 % all session (about 28 GB free). Nothing in the Docker store was unused for six months; the

  for the owner. The doctor (#234) reports disk, mirrors, TLS issuer and GPU runtime in seconds.
- The repository is four weeks old, so nothing in it is six months old either.

## Process lessons (each one cost time this session)

1. **A host g++ test run cannot see CMake or ROS compile errors.** A helper's host tests passed while its edit
   had mangled an existing `ament_add_gtest` line and broken the whole `motion_planner` build. Build under
   colcon in the image before believing a branch.
2. **Never share one install tree across branches.** Rebuilding one package from another branch silently removed
   a launch parameter and produced a false "failure" of the gravity pass.
3. **A wrapper's "completed, exit 0" is not a result.** Several builds and simulator runs reported success while
   the log showed a failure; read the log or the scorecard.
4. **Helper reports need independent verification.** A reported "14 passed" was one failure after a later edit;
   a "no change needed" audit was right; a claimed root cause held up only because the evidence was re-run.
5. **Mutation-check the tests that matter.** Several new tests passed on a broken implementation until a
   deliberate mutation exposed it (tool shift, a zero offset, an unused helper).
